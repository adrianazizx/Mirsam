# Milestone 4 demo — OCR

What exists: scanned pages become searchable text, in Arabic, English and mixed lines, read by
the quality pipeline in the background.

- **Engines:** Nuqta-Arabic-OCR 4B reads each page. Nuqta 0.8B re-reads every number and
  every unsure word, and the pipeline reconciles the readings without inventing anything
  (ADR 0030–0033).
- **Models:** downloaded on first use from Settings, with their size explained. Resumable,
  checksummed, and run locally by llama.cpp (ADR 0034).
- **Background jobs** (ADR 0035):
  - A quick draft of every page first (Apple Vision on macOS), so search works within
    moments. Each page is then replaced by the quality reading.
  - Progress, pause, resume, cancel. A job survives quitting the app.
- **The searchable PDF:** an invisible text layer with a box for every word, written by our
  own writer as an incremental update. The image is untouched, and Undo removes the layer.
  It reads back in logical order in this app and Preview, and in Chrome for Arabic lines
  (ADR 0035).
- **Pages needing review:** words the readers disagree on, corrected, or reordered, with
  confidence. Choosing one opens its page with the word marked.
- **The benchmark gate in CI:** the pipeline replayed on recorded model answers and scored
  against the stored baselines, plus a smoke run of the real model (ADR 0036).

Not yet:
- Tesseract as the draft on Windows and Linux (it is used if installed);
- the Vision helper shipped prebuilt and signed (M7);
- review mode's editing of a word (M6);
- Acrobat Reader (not installed here).

See `PROGRESS.md`.

Setup once: `scripts/dev-setup.sh`, `(cd apps/desktop && pnpm install)`, `node fixtures/generate.mjs`,
`node ocr-eval/generate.mjs`. On this Mac, first: `export PATH=/opt/homebrew/opt/rustup/bin:$PATH`.

## 1. OCR in the app (5 minutes, plus the model download once)

1. Make a scan to work on, with no text in it:
   ```bash
   mkdir -p /tmp/m4 && qpdf --empty --pages fixtures/out/chrome/contract-two-column.pdf \
     fixtures/out/chrome/mixed-inline.pdf fixtures/out/chrome/table-bilingual.pdf -- /tmp/m4/source.pdf
   cargo run -p safha-core --example ocr_document -- make-scan /tmp/m4/source.pdf /tmp/m4/scan.pdf 200
   cd apps/desktop && SAFHA_OPEN=/tmp/m4/scan.pdf pnpm tauri dev
   ```
2. Search for `الإيجار`: no hits, it is a scan.
3. Pick the OCR tool (the last tool in the rail), then **Recognize text in the document**.
   - The first time, the app offers the model download (5.5 GB with the runtime), then shows
     it in Settings.
4. Watch the panel:
   - all three pages turn searchable within a second ("searchable" in the bar);
   - then "Reading page 1 in quality mode…", about 25–45 s a page on an Apple-silicon Mac.
5. **Search** `الإيجار` again: three hits. Search `1234`: it finds `١٢٣٤`.
6. **Select and copy** a mixed line on page 2, then paste: the logical order, with English and
   numbers in place.
7. **Pause**, quit the app (Discard), start it again. The job resumes: the pages already read
   come back without being read again.
8. **Pages needing review:** choose a word. Its page opens with the word marked.
   **Next** and **Previous** step through them.
9. **Undo** takes the last page's text back off; the image underneath is untouched.
10. Switch to Arabic (**ع**): the panel and its progress bar run right to left.

## 2. The same headless, with timings

`ocr_smoke` installs packages through the app's own download manager into a store:

```bash
cargo run --release -p safha-core --example ocr_smoke -- --models /tmp/m4/models --package nuqta-0.8b \
  --image ocr-eval/out/images/syn-ar-plain-naskh-clean-300.png --truth ocr-eval/out/truth/syn-ar-plain-naskh-clean-300.txt
cargo run --release -p safha-core --example ocr_smoke -- --models /tmp/m4/models --package nuqta-4b --gpu \
  --image ocr-eval/out/images/syn-ar-plain-naskh-clean-300.png --truth ocr-eval/out/truth/syn-ar-plain-naskh-clean-300.txt
```

```bash
cargo run --release -p safha-core --example ocr_document -- /tmp/m4/scan.pdf /tmp/m4/half.pdf \
  --models /tmp/m4/models --state /tmp/m4/state --stop-after 1
cargo run --release -p safha-core --example ocr_document -- /tmp/m4/scan.pdf /tmp/m4/searchable.pdf \
  --models /tmp/m4/models --state /tmp/m4/state
```

Then open `/tmp/m4/searchable.pdf` in Chrome and Preview and copy page 2.

## Exit test (spec §12, M4), run on 2026-11-23

On an M3 Max (36 GiB), macOS 26, with Metal.

| Requirement | Result |
|---|---|
| Accuracy targets on `ocr-eval/` (spec §8 table) | ✓ **All five gates pass** (pipeline, set v2): clean Arabic 0.00% CER, 0.00% WER; clean English 0.00%; mixed 1.52%, 0 order errors; degraded Arabic 0.00%; fields 99.42% (170 of 171). Byte-identical to ADR 0033's run. **The numbers gate passes by one field.** |
| Ship gate: beat plain Tesseract in every Arabic category | ✓ (ADR 0030: by 9–60 points of CER) |
| Ship gate: beat the OCR in leading commercial editors | **Partly measured.** Apple Vision (Preview's OCR) is beaten in every category (ADR 0030). **Acrobat and ABBYY are not measured** (not installed; owner). |
| Ship gate: CI fails on any regression | ✓ `.github/workflows/ocr-benchmark.yml` (ADR 0036). A test mutation (removing "bit" from the order fix) failed it with 2 gates and 6 regressions. |
| A scanned bilingual document becomes searchable | ✓ The 3-page scan above, through the real job runner and engines. Arabic, English, mixed phrases and normalized digits are found. |
| Copied Arabic in correct order: **this app** | ✓ Every line, as it reads the born-digital original. On the evaluation set the searchable PDF reads back at 0.88% CER (45 pages without the two-column contract), 0.00% on clean, degraded, diacritized and other-typeface Arabic. |
| Copied Arabic in correct order: **Chrome** (PDFium) | ✓ for Arabic: every Arabic word in order (the born-digital original's are reversed). **Gap:** English runs inside Arabic lines come out word-reversed ("Pro 15 iPhone"), and brackets at direction changes flip; the same holds for Chrome's own PDFs (ADR 0005, ADR 0035). Measured with PDFium's text API, which is what Chrome copies from, not by copying in Chrome's window. |
| Copied Arabic in correct order: **macOS Preview** (PDFKit) | ✓ all but two lines. "INV-2026-00417" comes out flipped, and the line holding the misplaced "(64-bit)!" is scrambled. Preview breaks apart the original's Arabic. |
| Copied Arabic in correct order: **Acrobat Reader** | **Not tested:** Acrobat is not installed here (owner). |
| Background jobs: draft then quality; progress; cancel; restart | ✓ Drafts of 3 pages in 0.9 s. Quality pages 19–45 s. Stopped after one quality page and resumed: the kept results were written back without reading again. |
| Model download manager | ✓ The runtime (2 s), the 0.8B (1.1 GB, 91 s) and the 4B (5.5 GB, under 8 minutes) were installed through it, and each read a page: 0.8B on the CPU in 12.6 s at 0.00% CER; 4B on Metal in 9.7 s. |
| Hardware acceleration | ✓ Jobs run on the GPU when the runtime has a backend for it (Metal here). The CPU path is measured in ADR 0030 and 0032 and in the smoke run. |

**Not closed by this test:**
- **Real scans** (owner item 9). The set is synthetic, and the numbers margin is one field.
- **Acrobat** (reading and its OCR) and **ABBYY**.
- **The 4B on a typical Windows laptop's CPU.**
- **Copying in Chrome's own window**, as opposed to PDFium's API.
